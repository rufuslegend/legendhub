# LegendHUB 2.7.0 Production Release and 2.8 Cycle Design

**Date:** 2026-08-12
**Status:** Approved for implementation planning

## Goal

Promote the current verified `master` work to the immutable `v2.7.0` release,
deploy that exact release to the Legend production server, verify it with an
explicit rollback path, and then advance repository development metadata to
`2.8.0-beta` without deploying the new beta cycle.

## Scope and Constraints

- `master` is the primary branch. The release work starts from the current
  `origin/master` commit, `75ce61f1d77e26fa1bc36deea2243ea853304ca1`.
- The production SSH target is `legend`. The active deployment is the
  `legendhub260` Compose project in `/home/rufus/legendhub`.
- Production currently runs all three LegendHUB application images at
  `25ae0428d03e`; MySQL runs `mysql:5.7.44` and must not be recreated.
- Publish all three private images for `linux/amd64`:
  `tmckimmey/legendhub-www`, `tmckimmey/legendhub-python`, and
  `tmckimmey/legendhub-mysql-backup`.
- The release tag is `v2.7.0`. Existing release tags are immutable and remain
  untouched.
- The untracked root `docker-compose-prod.yaml` is user-owned and out of scope.
- Credentials and `.env` contents must never be displayed or committed.
- Production changes are limited to the server Compose image tags and the
  resulting recreation of the three LegendHUB application services.

## Release Metadata

The release commit changes all authoritative version surfaces together:

- `www/package.json` becomes `2.7.0`.
- The top-level and root-package versions in `www/package-lock.json` become
  `2.7.0`.
- The README version badge and development-version guidance become `2.7.0`.
- The current `CHANGELOG.md` section headed `2.6.1-beta` becomes `2.7.0`, dated
  2026-08-12. Its existing Added, Changed, and Fixed entries are the 2.7.0
  public release notes.

`node scripts/verify-release-version.js` must pass before the release commit is
eligible for tagging.

## Reusable Production Preflight

`scripts/preflight-production.sh` will take one required local argument: the
expected 12-character lowercase hexadecimal application-image tag. It validates
that input before opening SSH, passes it to the remote invocation, and derives
the expected mysql-backup, python, and www image names from it. The MySQL image
remains fixed at `mysql:5.7.44`.

The remote-only interface adds the expected SHA after `--remote`, followed by
the existing deploy root, cutover dump, and legacy rollback root. The preflight
remains read-only and continues to avoid rendering secrets in output.

Tests will establish the new contract before implementation. They cover:

- A valid expected SHA being passed through SSH and used for all three Compose,
  container, and local-image checks.
- Rejection of missing, malformed, uppercase, short, and long SHA arguments
  before SSH.
- Rejection of malformed remote invocation.
- Preservation of all existing service, container, image-ID, platform, backup,
  rollback, route, and non-mutation checks.

The pre-release production check runs with `25ae0428d03e`. The post-deployment
check runs with the new release commit's 12-character SHA.

## Release Creation and Image Publication

After metadata, preflight, and tests are complete:

1. Run the full release verification gates from a clean worktree.
2. Merge the release branch to `master` without rewriting shared history and
   push `master`.
3. Create annotated tag `v2.7.0` on the exact verified release commit and push
   that tag. Abort if the tag already exists locally or remotely.
4. Build and publish all three release images for `linux/amd64`, tagged with the
   release commit's 12-character SHA. Do not use a movable tag for deployment.
5. Inspect the published manifests and local references to verify the exact
   repositories, SHA tag, digests, and `linux/amd64` platform before production
   is changed.

The tag, image tag, deployed application version, and release commit must all
identify the same source state.

## Production Backup and Rollback Boundary

Immediately before changing production:

1. Re-run the read-only preflight against `25ae0428d03e`.
2. Record the current MySQL container ID and all active service image IDs.
3. Create a new timestamped, version-specific database dump outside the rolling
   backup filenames, under `/home/rufus/legendhub-release-backups`. The dump must
   be nonempty, gzip-valid, owned by the deployment user, and mode `600`.
4. Copy the active `/home/rufus/legendhub/docker-compose.yaml` to the same
   release-backup directory with a timestamped pre-2.7.0 name and mode `600`.
   Validate the copy's checksum against the active file. Leave `.env` in place
   and never print it.
5. Preserve the existing `25ae0428d03e` images as the immediate application
   rollback target. The older stopped `legendhub` project, its images, Compose
   files, database dump, and named volumes remain a second rollback boundary.

Any failed backup or rollback validation stops the deployment before production
is modified.

## Production Deployment

Update exactly the mysql-backup, python, and www image tags in the active server
Compose file to the release SHA. Use the maintainer's preferred `vi` tooling for
the server-side edit, then validate both the file diff and rendered Compose
configuration before pulling or recreating services.

Pull the three exact immutable images, then recreate only `mysql-backup`,
`python`, and `www` with dependencies disabled. Do not run `down`, do not remove
volumes, and do not recreate `mysql`. Verify that the MySQL container ID remains
unchanged across the operation.

If an image pull, recreation, health check, or release verification fails,
restore the saved Compose file and recreate those same three application
services at `25ae0428d03e`. Confirm the unchanged MySQL container, restored image
IDs, service health, backups, and routes before ending the rollback.

## Production Verification

The deployment is successful only when all of these checks pass:

- The active Compose file, container configuration, and running image IDs match
  the exact release-SHA images for all three LegendHUB services.
- All application images report `linux/amd64`.
- All four containers are running with zero restarts; MySQL is healthy and has
  the same container ID recorded before deployment.
- Current daily private and public backup artifacts remain present and valid,
  and the new pre-2.7.0 backup remains nonempty, private, and gzip-valid.
- The parameterized production preflight passes with the release SHA.
- `/`, `/feedback.html`, `/changelog`, `/builder/`, `/items/`, `/mobs/`,
  `/quests/`, `/wiki/`, and `/login.html` return HTTP 200 both locally through
  port 7000 and publicly through `https://www.legendhub.org`.
- Public version and asset references report `2.7.0`.
- The shared picker's shipped markup and CSS retain its four-column grouping,
  half-viewport desktop cap, responsive stacking, compact reset control, and
  current label and surface styling.

## Starting the 2.8 Cycle

Only after production 2.7.0 passes every verification gate, create a separate
post-release commit on `master` that:

- Changes `www/package.json` and both relevant lockfile version values to
  `2.8.0-beta`.
- Changes the README badge and development-version guidance to `2.8.0-beta`.
- Adds a new top changelog heading, `## [2.8.0-beta] - 2026-08-12`, ready for
  subsequent public-facing changes while preserving the completed 2.7.0 notes.
- Passes the release-version verifier and proportionate tests.

Push this post-release commit to `master`. Do not create a 2.8 tag, publish 2.8
images, or deploy 2.8 to either Dunwich or Legend. Production remains pinned to
the immutable 2.7.0 release commit even though `master` advances into the next
development cycle.

## Success Criteria

- `v2.7.0` exists once and points to the verified release commit.
- All three private release images exist under that commit's 12-character SHA
  and are `linux/amd64`.
- Legend production is healthy and pinned to those three images, with its MySQL
  container and volumes preserved.
- A fresh database backup, Compose rollback copy, and the previous
  `25ae0428d03e` application images provide a tested immediate rollback path.
- `origin/master` subsequently identifies `2.8.0-beta`, while production remains
  on 2.7.0 and no 2.8 artifact has been published or deployed.
