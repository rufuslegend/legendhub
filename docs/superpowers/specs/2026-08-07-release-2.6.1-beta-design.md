# LegendHUB 2.6.1-beta Corrective Release Design

## Goal

Prepare `2.6.1-beta` as the next LegendHUB release target while correcting the
public changelog text that still describes the promoted `2.6.0` release as a
beta. Preparation is local only: this work does not push, tag, publish images,
or deploy.

## Versioning Policy

LegendHUB uses the middle version number for API-level changes. The final dot
number may contain substantial application changes. The exact target for this
work is the valid semantic prerelease version `2.6.1-beta`.

The immutable `v2.6.0-beta` and `v2.6.0` tags remain unchanged. The released
`2.6.0` changelog section also remains as historical release evidence.

## Changelog Structure

Add a new top release section:

```text
## [2.6.1-beta] - 2026-08-07
```

Its initial `Fixed` entry explains that the public changelog release text was
corrected after the `2.6.0` promotion. Keep the existing `2.6.0` section below
it without rewriting its released feature notes.

Change the changelog introduction to say that tracked public history begins
with version `2.6.0`. This introductory value describes the oldest retained
release heading, not the current application version.

## Release Metadata

Update the current release version to `2.6.1-beta` in:

- `www/package.json`
- the root package and top-level version fields in `www/package-lock.json`
- the README badge text and badge URL

The existing release-version verifier remains the source of truth for agreement
between the current changelog heading, package metadata, lockfile metadata, and
README badge.

## Regression Protection

Extend `scripts/verify-release-version.js` so it also parses the changelog
introduction and requires its "beginning with version" value to equal the
oldest retained semantic-version release heading. Ignore an optional
`Unreleased` section when determining release headings.

This generalized rule catches the actual `2.6.0-beta`/`2.6.0` mismatch without
hard-coding either version and continues to work as new sections are added.
Malformed, missing, or mismatched introduction metadata fails verification
with a changelog-specific error.

Add script-level regression tests before changing the verifier:

- a changelog whose introduction matches its oldest release is accepted;
- a changelog whose introduction contains the stale prerelease is rejected;
- multiple release headings still use the newest heading as the current
  package version and the oldest heading as the beginning version.

The web changelog route needs no behavior change. Its Docker image already
copies root `CHANGELOG.md` verbatim and renders that file through
`CHANGELOG_PATH`.

## Verification

Run the focused release-version tests first, then the release verifier and the
repository's existing release gates: script tests, web tests, CSS lint, shell
syntax checks, Compose validation where supported, and Git whitespace/status
checks. Confirm the prepared branch contains only intended release and
regression-test changes.

No existing tag may be moved or deleted. Publishing a new tag, publishing the
three private `linux/amd64` image repositories, or deploying the prepared SHA
requires separate explicit authorization after local verification.
